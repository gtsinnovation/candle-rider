# Fix: the landing window scales with speed, so fast coins are *more* forgiving than slow ones

| Field | Value |
|---|---|
| File | `client/src/scenes/paths/TrenchesScene.js` |
| Category | Gameplay correctness / Balance |
| Severity | high |
| Effort | Medium |
| Behaviour change | yes — falling becomes possible at high speed and impossible-by-accident at low speed |

## Problem

Landing is tested with a window that scales linearly with the current scroll
speed (`TrenchesScene.js:1238`):

```js
const nearZ = Math.abs(c.mesh.position.z - player.position.z) < CANDLE_D / 2 + speed * 0.55;
```

`CANDLE_D / 2` is `0.6`, so the window is `0.6 + speed × 0.55` world units.
Candles are spawned one per cursor step into a **random** lane, spaced
`(3.4 + rand × 1.4) × WORLD_SCALE` = **2.55–3.6 units** apart
(`TrenchesScene.js:853`, `:1223`).

Comparing the window against that spacing, using each coin's real speed
range (`base` → `base + cap`, per `i4.md`):

| Coin | speed range | landing window | rows inside the window |
|---|---|---|---|
| `$STABLE` | 3.2 → 5.5 | 2.36 → 3.63 u | **0.7 → 1.2** |
| `$SAFU` | 4.05 → 7.2 | 2.83 → 4.56 u | 0.9 → 1.5 |
| `$VOLT` | 8.1 → 14.4 | 5.06 → 8.52 u | 1.6 → 2.8 |
| `$APEMAX` | 15.0 → 26.5 | 8.85 → **15.18 u** | 2.9 → **5.0** |
| `$LEGEND` | 17.0 → 30.5 | 9.95 → 17.38 u | 3.3 → 5.7 |

At `$APEMAX`'s top speed the player is "on" any candle within ±15 units —
five rows in either direction. Something is essentially always in range, so
the player is magnetically caught and **cannot fall**. At `$STABLE` the
window is narrower than the gap between consecutive rows, so when the
current candle scrolls past there may be nothing in range at all and the
player drops into the void with no available input.

The difficulty ordering is therefore inverted: the coin sold as "Blue Chip
Reserve / safest" is the only one where an accidental death is likely, and
the coin sold as "Maximum Ape" removes the platforming failure state
entirely.

The jump reach has the same defect from the same cause. With
`GRAVITY = -18` and `JUMP_LAUNCH_VEL = 7.5`, air time is `2 × 7.5 / 18 =
0.83s`, so a jump covers `0.83 × speed` units:

| Coin | jump reach at top speed | rows cleared |
|---|---|---|
| `$STABLE` | 4.6 u | ~1.5 |
| `$APEMAX` | 22.0 u | ~7 |

A jump on `$APEMAX` flies over seven rows; on `$STABLE` it barely clears
one. Both the landing check and the jump get *more* lenient exactly where
the game is supposed to get harder.

## Root cause

`speed × 0.55` treats leniency as a **distance**. Leniency is really a
**time** — how many milliseconds of imprecision the player is allowed. A
distance-based grace term grows without bound as the run ramps, while row
spacing stays fixed, so the ratio between them (which is what actually
determines difficulty) drifts by ~7× across the coin roster.

## Recommended Fix

Two parts. Either alone makes things worse; they need to land together.

**1. Make the grace constant in time, not distance.** Keep the `speed`
multiplication (it is what makes the check frame-rate and speed
independent — the original intent) but scale it by a small grace *duration*
rather than 0.55:

```diff
-const nearZ = Math.abs(c.mesh.position.z - player.position.z) < CANDLE_D / 2 + speed * 0.55;
+// LANDING_GRACE_SECONDS is a TIME allowance, not a distance. 0.55 here was
+// read as "a bit of slack" but is 0.55 SECONDS of travel — 15 units at
+// $APEMAX's top speed, which catches the player on any of five rows and
+// removes the void-fall failure state on every fast coin.
+const nearZ = Math.abs(c.mesh.position.z - player.position.z) < CANDLE_D / 2 + speed * LANDING_GRACE_SECONDS;
```

```diff
+const LANDING_GRACE_SECONDS = 0.10; // ~100ms of timing slack at any speed
```

That gives 0.92 u at `$STABLE` base and 3.25 u at `$APEMAX` top — a
consistent ~0.3 rows of slack instead of 0.7–5.0.

**2. Guarantee a landable platform in every lane, every row.** Part 1 alone
would make `$STABLE` unplayable, because a single random-lane candle per
cursor step means the player's lane frequently has no platform within any
sane window. Spawn a candle per lane per step and let the *colour* be the
hazard:

```diff
-  let cursorZ = -4 * WORLD_SCALE;
-  for (let i = 0; i < 24; i++) {
-    spawnCandle(cursorZ);
-    cursorZ -= (3.4 + Math.random() * 1.4) * WORLD_SCALE;
-  }
+  // One candle per LANE per step: the decision is which colour to ride,
+  // not whether a platform happens to exist in your lane. Voids become a
+  // deliberate hazard (see holeChance below) instead of an artefact of
+  // random lane assignment.
+  let cursorZ = -4 * WORLD_SCALE;
+  for (let i = 0; i < 24; i++) {
+    spawnRow(cursorZ);
+    cursorZ -= (3.4 + Math.random() * 1.4) * WORLD_SCALE;
+  }
```

where `spawnRow(z)` calls `spawnCandle(z, lane)` for lanes 0–2, keeps the
existing anti-streak rule, guarantees at least one green per row, and skips
a lane with probability `holeChance` to create a real void — never all three.

Row spacing stays **fixed** deliberately. That is what makes fast coins
hard: rows arrive faster, so the player has less time to read them.
Reachability is solved by the layout guarantee, not by widening the window.

## Validation

This is what the prototype in this project (`Trenches Core Loop.dc.html`)
now does, after hitting the same bug from the other direction — a
speed-scaled window made `$STABLE` die in ~1.5 seconds with no possible
input, while `$VOLT` survived indefinitely. With fixed row spacing, one
candle per lane per row, and grace exposed as a tunable, all five coins are
playable and the difficulty ordering matches the coin descriptions. The
`Landing grace` tweak in that file demonstrates the axis directly: at a wide
setting the fast coins stop being able to kill you.

## Knock-on

- The comment at `:1236` ("so jumping straight up doesn't miss...") is the
  justification for the current value and should be updated — the concern
  is real, but 100ms covers it; 550ms overshoots by 5×.
- Consider whether `JUMP_LAUNCH_VEL` should be re-tuned once landing is
  strict. Clearing ~7 rows at `$APEMAX` was previously masked by the fact
  that the player could not miss anyway.
- Void-fall becomes a genuine death cause on fast coins for the first time,
  which will change run-length telemetry. Expect shorter runs on
  `$APEMAX`/`$LEGEND` — that is the fix working, not a regression.
