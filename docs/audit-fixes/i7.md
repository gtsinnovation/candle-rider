# Fix: HUD and War Room rebuild their innerHTML on every state change (up to 60×/sec during play)

| Field | Value |
|---|---|
| Files | `client/src/ui/HUD.js`, `client/src/scenes/WarRoomScene.js`, `client/src/main.js` |
| Category | Performance |
| Severity | medium |
| Effort | Low |
| Behaviour change | none (visually identical) |

## Problem

Both DOM views subscribe to `state:changed` and respond by discarding and
re-parsing their entire subtree.

**`HUD.js`** — `render(state)` assigns `el.innerHTML = ...` with 8 stat rows.
`GameState` emits `state:changed` on every Bag accrual, and Bag accrues on
every green landing plus continuous riding, so during a run this fires up to
**60×/sec**. Each fire re-parses ~10 elements and re-lays-out the panel.
`docs/FEATURES.md` already lists this as a known unfixed item.

**`WarRoomScene.js`** — same pattern, worse payload: `render()` does
`el.innerHTML = ''` and rebuilds 5 cards, each containing an
`<img src="${heroArtUrl(path.id)}">`. Those five hero PNGs total **18.8 MB**
(see `i8.md`). Every `state:changed` while the hub is showing destroys and
recreates all five `<img>` elements, forcing the browser to re-decode them
even when they are served from cache. The hub fires this rarely today, but
any future hub-side state (a currency ticker, an energy regen timer) turns
it into a stutter.

The nesting is the giveaway in both files: nothing about the markup changes
between renders — only the numbers inside it.

## Root cause

`innerHTML =` is being used as a state-diffing mechanism. The template is
static; only text content varies. Rebuilding the tree to change a number is
the most expensive way available to do it, and there is no coalescing, so N
state changes in one frame cost N full rebuilds.

## Recommended Fix

Two changes, both mechanical.

**1. Build once, update text nodes.** Mark the varying values and write only
those:

```diff
 export function mountHUD(container, gameState) {
   injectResponsiveStyles();
   const el = document.createElement('div');
   el.id = 'hud';
   el.style.cssText = `...unchanged...`;
   container.appendChild(el);
 
-  function render(state) {
-    el.innerHTML = `
-      <div class="hud-title" ...>DEGEN WARRIOR LVL ${state.level}</div>
-      <div>Bag: $${Math.round(state.bag ?? 0).toLocaleString()}</div>
-      ...
-    `;
-  }
+  // Static structure, built once. Only the [data-f] text nodes are ever
+  // written after this — innerHTML was being used as a diffing mechanism
+  // for what is really eight numbers.
+  el.innerHTML = `
+    <div class="hud-title" style="font-size:16px;font-weight:700;margin-bottom:6px;">DEGEN WARRIOR LVL <span data-f="level"></span></div>
+    <div>Bag: $<span data-f="bag"></span></div>
+    <div>PNL: <span data-f="pnl"></span></div>
+    <div>Health: <span data-f="health"></span>%</div>
+    <div>Energy: <span data-f="energy"></span>%</div>
+    <div>Conviction: <span data-f="conviction"></span>%</div>
+    <div>Reputation: <span data-f="reputation"></span></div>
+    <div>Conviction Shards: <span data-f="shards"></span></div>
+  `;
+  const fields = {};
+  el.querySelectorAll('[data-f]').forEach((n) => { fields[n.dataset.f] = n; });
+  const shown = {};
+
+  function paint(state) {
+    const next = {
+      level: state.level,
+      bag: Math.round(state.bag ?? 0).toLocaleString(),
+      pnl: (state.pnl ?? 0).toFixed(2),
+      health: Math.round(state.health),
+      energy: Math.round(state.energy),
+      conviction: Math.round(state.conviction),
+      reputation: (state.reputation ?? 0).toLocaleString(),
+      shards: state.convictionShards ?? 0,
+    };
+    // Only touch the DOM for values that actually moved.
+    for (const k in next) {
+      if (shown[k] !== next[k]) { fields[k].textContent = next[k]; shown[k] = next[k]; }
+    }
+  }
```

**2. Coalesce to one paint per frame.** Several `state:changed` events can
fire in a single tick; only the last one is visible to the player:

```diff
+  // Multiple state changes can land in one frame (bag accrual + streak +
+  // health). Collapse them — the player can only see the final value.
+  let queued = null;
+  let latest = null;
+  function schedule(state) {
+    latest = state;
+    if (queued !== null) return;
+    queued = requestAnimationFrame(() => { queued = null; paint(latest); });
+  }
+
-  render(gameState.snapshot());
-  const unsubscribe = eventBus.on('state:changed', render);
+  paint(gameState.snapshot());
+  const unsubscribe = eventBus.on('state:changed', schedule);
   return () => {
     unsubscribe();
+    if (queued !== null) cancelAnimationFrame(queued);
     el.remove();
   };
 }
```

**3. Same treatment for the War Room, but never rebuild the `<img>`.** Cards
are created once; re-render only writes the mastery line:

```diff
-  function render() {
-    const state = gameState.snapshot();
-    el.innerHTML = '';
-    PATHS.forEach((path) => { ...creates card + <img> every time... });
-  }
+  // Cards (and crucially their hero <img>, 18.8 MB across the five paths)
+  // are built once. A state change only rewrites the mastery number —
+  // rebuilding innerHTML forced a re-decode of every hero image.
+  const masteryFields = {};
+  function buildCards() { /* existing card construction, run once */ }
+  function paintMastery() {
+    const state = gameState.snapshot();
+    PATHS.forEach((path) => {
+      const next = `Mastery Lv. ${state.pathMastery[path.id] ?? 0}`;
+      if (masteryFields[path.id].textContent !== next) {
+        masteryFields[path.id].textContent = next;
+      }
+    });
+  }
```

If a path's `unlocked` state can change while the hub is mounted, handle
that by toggling the card's style/listener rather than rebuilding it.

**4. Keep the HUD's teardown.** `main.js` currently discards it:

```diff
-    mountHUD(container, gameState);
+    const teardownHUD = mountHUD(container, gameState);
```

To be precise about what this is: the HUD lives for the whole app lifetime,
so the discarded handle is not itself a leak today — but it means the HUD
can never be unmounted, and it is what `docs/FEATURES.md` points at when it
describes the 60/sec re-render as unfixable "since its teardown is discarded
in `main.js`". Capturing it also lets the `beforeunload` path cancel the
pending `requestAnimationFrame` cleanly.

## Why not throttle instead

A `setTimeout`/interval throttle would also cut the cost, but it decouples
the HUD from the frame clock and can show a stale number at the moment a run
ends. Coalescing on `requestAnimationFrame` gives exactly one paint per
displayed frame, which is the ceiling worth paying for and never lags behind
what is on screen.

## Validation

The prototype in this project (`Trenches Core Loop.dc.html`) hit the same
class of problem with its Bag Value chart, which is why that chart samples
on a fixed 350 ms interval rather than per frame — and its HUD publishes
state at ~11 Hz rather than per frame for the same reason. Both are visually
indistinguishable from per-frame updates.
