# Fix: 46.7 MB of PNG art, ~27 MB of it downloaded before the first run, cached forever with no eviction

| Field | Value |
|---|---|
| Files | `client/public/assets/**`, `client/public/sw.js`, `client/src/scenes/WarRoomScene.js`, `client/src/scenes/paths/TrenchesScene.js` |
| Category | Performance / Mobile |
| Severity | high |
| Effort | Medium |
| Behaviour change | none visually, if re-encoded at display resolution |

## Problem

`client/public/assets/` is **46.7 MB across 23 PNGs**:

| Group | Files | Bytes | Note |
|---|---|---|---|
| `heroes/` | 7 | **21.7 MB** | 1.36–4.46 MB each |
| `bosses/` | 5 | **17.8 MB** | 3.12–3.99 MB each |
| `coins/` | 11 | **6.8 MB** | ~0.57–0.66 MB each |
| icons | 2 | 0.4 MB | `icon-512.png` alone is 341 KB |

None of it is displayed anywhere near its encoded resolution:

- **Hero cards** render at `width:100%; height:200px` inside a 220px-wide
  card (`WarRoomScene.js`) — roughly **220×200 CSS px**, fed by files
  averaging 3.1 MB. `soft-rug-titan.png` is 1280×1920.
- **Coin discs** are `CircleGeometry(0.55, 32)` in a 3D scene at
  `WORLD_SCALE 0.75` — a few hundred device pixels at most, fed by ~600 KB
  each.
- **The hero sprite** uses the already-cut-down
  `trenches-back-cutout.png` (1.6 MB) at `HERO_HEIGHT = 2.1` world units.

### What a first-time player actually downloads

| Screen | Assets pulled | Bytes |
|---|---|---|
| War Room hub | 5 hero PNGs (`heroArtUrl` per path, all 5 cards visible) | **18.8 MB** |
| Trenches coin room | 11 coin PNGs (`TextureLoader` per coin, built eagerly) + back-cutout | **8.4 MB** |
| **Before a single run** | | **≈ 27 MB** |

On a phone in the trenches — the stated target, with a PWA install prompt and
`touch-action: none` tuning to prove it — that is a multi-second stall on the
hub before anything is interactive, and it is paid before the player has seen
any gameplay.

### The service worker makes it permanent, not smaller

`sw.js` precaches only 4 URLs, so there is no 46 MB install cost — good. But
the `fetch` handler is cache-first with **no size cap, no eviction, and no
revalidation**:

```js
if (event.request.method === 'GET' && response.ok && url.origin === self.location.origin) {
  const clone = response.clone();
  caches.open(CACHE_NAME).then((cache) => cache.put(event.request, clone));
}
```

Three consequences:

1. **Unbounded growth.** Every art file the player ever touches accumulates
   in Cache Storage, trending toward the full 46.7 MB. iOS Safari evicts
   whole origins under storage pressure, so a large art cache raises the
   odds of losing the *shell* cache too — the thing the SW exists to keep.
2. **Art can never be updated.** Cache-first with no revalidation means a
   replaced PNG is never fetched again until `CACHE_NAME` is bumped by hand.
   Re-encoding the assets per this patch will therefore ship as a no-op to
   every returning player unless the version is bumped in the same commit.
3. **404s are cached too** — `response.ok` guards that, but the five
   art-less coins from `i5.md` each cost a failed round-trip per room entry
   until that patch lands.

## Recommended Fix

**1. Re-encode at display resolution, in a modern format.** This is where
essentially all of the win is:

| Group | Now | Target | Est. after |
|---|---|---|---|
| `heroes/` (cards) | 3.1 MB avg PNG | 440×400 WebP (2× the 220×200 box) | ~80 KB each |
| `bosses/` | 3.6 MB avg PNG | 1024×1536 WebP (shown large) | ~350 KB each |
| `coins/` | 600 KB avg PNG | 256×256 WebP | ~30 KB each |
| `icon-512.png` | 341 KB | 512×512 WebP/optimised PNG | ~25 KB |

Estimated total: **~2.5 MB, down from 46.7 MB — a ~95% cut** with no visible
change at the sizes these are actually drawn. Keep the PNG originals out of
`client/public/` (they are source art, not deliverables).

Note `bosses/soft-rug-titan.png` has **no alpha channel** — it carries its
own dark background, so anything that billboards it in 3D draws a visible
rectangle. Cut it out like the hero art was (`trenches-back-cutout.png`,
described in `FEATURES.md` as "background removed programmatically") or
composite it as a framed portrait. The prototype in this project hit exactly
this and moved the Titan into a circular framed portrait for that reason.

**2. Stop loading all 11 coin textures up front.** The coin room builds
every disc eagerly in the `TRENCHES_COINS.map(...)`. Load the focused coin
plus its immediate neighbours, and fill the rest in on idle — or once the
files are ~30 KB each, this stops mattering and can be left alone.

**3. Give the boss art its own trigger.** Boss PNGs are the second-largest
group and are not shown at all until an encounter exists. Load on encounter
start, not on scene mount.

**4. Bound and version the runtime cache:**

```diff
-const CACHE_NAME = 'candle-rider-v1';
+// Bump on every art or shell change — cache-first never revalidates, so a
+// replaced asset is invisible to returning players until this changes.
+const SHELL_CACHE = 'candle-rider-shell-v2';
+const ART_CACHE = 'candle-rider-art-v2';
+const ART_MAX_ENTRIES = 40;
```

Put art in its own bucket with a trim step after each insert, so art
pressure can never evict the shell:

```diff
+async function putCapped(cacheName, request, response, maxEntries) {
+  const cache = await caches.open(cacheName);
+  await cache.put(request, response);
+  const keys = await cache.keys();
+  // FIFO is fine here — art is small and re-fetchable.
+  for (let i = 0; i < keys.length - maxEntries; i++) await cache.delete(keys[i]);
+}
```

and route `/assets/` requests through it. Keep API calls uncached exactly as
they are — that part is right.

**5. Consider stale-while-revalidate for art** rather than pure cache-first:
serve the cached copy immediately, fetch a fresh one in the background. That
removes the "art can never be updated" trap without costing the player a
wait.

## Sequencing

Re-encode (1) and bump `CACHE_NAME` (4) must ship **in the same commit**, or
returning players keep the 46 MB versions indefinitely. (2) and (3) are
optional once (1) lands.
